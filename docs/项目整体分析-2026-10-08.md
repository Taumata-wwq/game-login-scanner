## 一、项目定位

Windows 桌面工具。解决一个很具体的问题：**游戏登录界面弹出二维码时，用本机已登录的账号直接确认，不必掏手机扫、也不必手输账号**。

| 厂商 | 游戏 | 登录渠道 |
| --- | --- | --- |
| 米哈游 | 崩坏3 / 崩坏：星穹铁道 / 原神 / 绝区零 | 官服（米游社）/ B 服（Bilibili） |
| 鹰角 | 明日方舟：终末地 / 明日方舟 | 鹰角账号 |

核心使用场景有两个：**屏幕扫码**（游戏在自己机器上）与**直播抢码**（跟 B 站直播间的放码画面抢时间，延迟约 0.4 秒）。

账号只保存登录令牌、不保存密码，令牌用 Windows DPAPI 加密落盘（绑定当前用户，换机换用户无法解密）。

## 二、技术栈与分层

```
┌─ 前端 ────────────────────────────────────────────────┐
│ src/index.html  2,048 行单文件，原生 HTML/CSS/JS       │
│ src/verify.html 人机验证窗口（极验 GT3/GT4）           │
│ 无构建链、无框架；26 个 invoke + 2 个 listen           │
└───────────────────────────────────────────────────────┘
                    ↕ Tauri IPC（含裸二进制帧）
┌─ 命令层 ──────────────────────────────────────────────┐
│ lib.rs 1,598 行：27 个命令 + AppState + 运行时装配      │
└───────────────────────────────────────────────────────┘
┌─ 业务层 ──────────────────────────────────────────────┐
│ scan.rs        扫码主流程编排（776）                    │
│ live.rs        直播流捕获（1,991）  hls.rs HLS 解析(436)│
│ duplication.rs DXGI 桌面复制取帧（1,041）               │
│ qr.rs 二维码识别/生成（370）                            │
│ screenshot.rs GDI 兜底（134）  clipboard.rs 剪贴板(108) │
└───────────────────────────────────────────────────────┘
┌─ 协议层 sdk/ ─────────────────────────────────────────┐
│ mihoyo(352) official(351) bili(318)                    │
│ cred_login(413) hypergryph(139)                        │
└───────────────────────────────────────────────────────┘
┌─ 基础层 ──────────────────────────────────────────────┐
│ http.rs(516) 自写 HTTP/1.1 + rustls/schannel 双栈      │
│ config.rs(542) crypto.rs(172) constants.rs(123)        │
└───────────────────────────────────────────────────────┘
```

**关键选型及其理由**（均记录在代码注释中，非拍脑袋）：

- **Tauri 2 关闭全部默认特性**，只留 `wry`：前端仅两个内嵌 HTML、静态 capabilities、不弹系统对话框。
- **不用 reqwest / ureq**：ureq 会拖入 `url→idna→icu_*` 数百 KB；复用直播侧已有的 rustls 自己写 HTTP/1.1。
- **不用 rxing，用 rqrr + zedbar**：rxing 拖 `regex/chrono-tz/encoding` 约 1.7 MB；zedbar 识别率更高（识别下限 130px → 100px）。
- **不用 screenshots / arboard**：各拖一份 image 全家桶，直接走 Win32 GDI / CF_DIB 手写解析。
- **逐 crate 调 opt-level**：openh264 的 C 代码单独 O2（体积优先的 "z" 会让 1080p 软解跟不上 60fps），事件驱动类 crate 全部 "z"。产物 **4.85 MB**。
- **vendor 化 openh264-sys2**：原版 NASM 在中文路径下静默降级，导致解码慢。

## 三、三条核心链路

### 3.1 屏幕扫码（`scan.rs`）

```
剪贴板读图（限时 500ms，超时直接跳过）
   ↓ 未命中
60Hz 循环：
  DXGI 桌面复制取帧（无新帧零成本跳过）
    → 抽样指纹去重（光标闪烁不触发解码）
    → ROI 优先（上轮命中位置外扩 96px 先解）
    → 2×2 降采样快路径（≥1600px 才启用）
    → 全分辨率解码（节流 400ms）
    → zedbar 兜底（节流 500ms，最贵路径）
   ↓ 解出文本
extract() 判定码类型 → 当前渠道账号确认
```

码类型判定：`qr_code_in_game.html?ticket=`（游戏登录码，含 `biz_key` 决定端点）、`mobile.html?tk=`（米游社通行证码，忽略）、`hypergryph://scan_login?scanId=`（鹰角）。

**设计上有个明确取舍**：登录码是通用的，平台无法从 URL 区分，所以不做多渠道轮询，只用「当前选中的那个账号」确认。B 服账号在选中时后台预校验并缓存 `bh_info`，命中码后确认零等待。

失败治理很细：同一票据失败 3 次后跳过、失败退避 1.5s、成功限流 2 分钟 10 次（触发后停止扫描但不执行成功后动作，因为服务端其实已确认）、`select!` 与停止信号竞争以即时取消挂起请求。

### 3.2 直播抢码（`live.rs` + `hls.rs`）

```
房间号 → resolve_stream（v2 接口，无 flv 才回退 HLS）
      → 多 durl 按 host 去重作 CDN 候选池
      → HttpFlvReader（手写 GET + 302 跟随 + chunked）
      → FLV tag 循环 / HLS fMP4 分片（LL-HLS）
      → avcc→annexb 转码 + strip_sps_vui（否则 dsNoParamSets）
      → openh264 解码（Flush::NoFlush + DecodeFrame2(NULL) 裸 API）
      → I420 帧总线（队列上限 6）
      → crop_frame（预览）/ take_scan_frame（扫码）
```

低延迟靠**追帧锚点**：维护 `(media_ts, Instant)`，lag > 400ms 就进入 skipping 状态只读不解码，直到 IDR 重建解码器。清晰度降级由两个条件触发：解码连续失败 40 次，或单会话追帧 4 次。

HLS 路径是后加的能力（`hls.rs` 零新增依赖，手写 m3u8 + fMP4 box 解析，含 B 站私有 `EXT-BILI-AUX` 关键帧标记）。实测端到端已跑通：12.27s 内解出 328 帧 1280×720（见 `hlst.log`）。

### 3.3 取帧（`duplication.rs`）

一个进程级单例 + 每显示器一条 OS 线程（`game-scanner-dup-bus`，15ms 轮询）。总线只做 GPU→GPU 拷贝，CPU 侧转换留给消费者——职责分离清晰。

两套消费者 ROI 取并集：扫码 ROI 与预览 ROI 同时存在时只拷并集区域。三种画面源按场景切换：**实时帧**（空闲）、**瓦片底图**（拖拽/缩放中，33ms 增量更新 64px 瓦片）、**暂停快照**（省 GPU）。

脏矩形过滤、内容指纹（FNV-1a）去重、`frame_id` 多消费者 seq 去重、禁止上采样（避免放大时黑网格）——优化密度很高。

## 四、工程质量：做得好的地方

1. **注释质量是本项目最大的资产**。不是"这个函数做什么"，而是"为什么必须这样、不这样会怎样"，且带实测数据：

   > "默认每帧 flush 冲掉参考链，实测 1080p60 仅解出 110/1261"
   > "禁止再写 JS startDragging 兜底（两处竞争导致约 50% 拖不动）"
   > "schannel 对 B站 CDN 长连接有读乱码/EOF"

   这类注释直接把踩坑成本固化了下来。

2. **性能优化是全栈、有度量的**：从 GPU 拷贝到 IPC 负载（24 字节"画面未变化"语义让前端直接跳过重绘）到前端空闲降频（140ms），每一层都有对应手段，且都注明了实测依据。

3. **异步竞态治理一致**：后端用 `login_qr_seq` 代际号防并发切换渠道时旧请求覆盖新会话；前端用 `previewGen` / `qrStartSeq` / `liveSeq` 三个令牌防快速 start/stop 导致的帧率叠加。

4. **状态单一真源在 Rust**：前端只持 config 快照，写操作统一走「invoke 写命令 → 重拉 get_config → renderAll」，避免了双端状态漂移。

5. **容量与自愈考虑**：`Broken` 时从 map 移除显示器，下次 `get_or_create` 自动重建（自愈锁屏/切显卡/设备丢失）；配置原子写 + 损坏自动备份；日志 2MB 轮转；`remove_session_if` 用 `Arc::ptr_eq` 防误删新会话。

6. **构建可复现性有照顾**：`rust-toolchain.toml` 固定 stable + rustfmt + clippy；CI 里 `cargo fmt --check` 与 `clippy -D warnings` 都配了。

## 五、风险与问题清单

### P0 — 影响安全或导致功能永久失效

| # | 位置 | 问题 |
| --- | --- | --- |
| 1 | `bili.rs` 登录日志 | `log::info!("[B站SDK登录] {}", &resp.to_string()[..600])` 会把 **access_key 明文写进日志文件**，而日志长期留存于 `%APPDATA%`。与"DPAPI 加密落盘"的安全承诺直接冲突。 |
| 2 | `duplication.rs:610/618` | `tile_delta` 先 `mem::take` 清空 `dirty`，若随后的 `Map` 失败提前返回，脏标记永久丢失 → **拖拽底图再也不更新（冻结）**，且无恢复路径。 |
| 3 | `duplication.rs:419/498/615` | 三处 Map…Unmap 之间无 `catch_unwind`（只有总线线程有）。一旦 panic 会毒化 mutex 且 staging 停在已 Map 状态，后续 Map 恒失败 → **永久降级 GDI**。 |
| 4 | `index.html` `showCaptcha` | 轮询的 `catch(e){ return; }` 未 `clearInterval(timer)`，后端持续报错时**每 400ms 永久轮询**；重复触发还会叠加多个 interval。 |
| 5 | `duplication.rs:390` | 全程只取 `GetFrameDirtyRects`，**未处理 MoveRects**。滚动/拖动窗口只产生 MoveRects 时，`mark_dirty_tiles` 在 `n==0` 直接 return 不标脏 → 瓦片底图显示陈旧内容。 |

### P1 — 稳定性与正确性

6. `live.rs`：`dec_fails` 成功时不复位，是会话累计值 → 长跑后偶发错误累积到 40 次会**误触发清晰度降级**。
7. `live.rs:1921`：FLV 路径在 `decode()` 已出帧后再调 `decode_frame2(NULL)`，可能**重复推送同一帧**。
8. `live.rs:983`：`crop_frame` 自持锁至函数结束，YUV→RGBA 转换**在锁内**执行，与 893 行"锁外转换"注释自相矛盾，会阻塞扫码取帧。
9. `live.rs:992`：`None => f.queue.front().unwrap()` 为不可达 panic 分支。
10. `mihoyo.rs`：`BH_INFO_CACHE` 无 TTL / 失效接口 → 凭据过期或切号后仍返回旧值。
11. `hypergryph.rs`：`post_json` 的 `token` 参数从未被 `scan_login`/`update_scan_status` 使用 → **`cred` 头实际不发送**（死参数，疑似遗漏）。
12. `cred_login.rs`：`mihoyo_login_sms` 的 `_aigis` 被丢弃 → 登录若触发极验返回 `NeedCaptcha`，上层**无法带 aigis 重试，死路**。
13. `index.html` `saveCfg`：每次上传**整个 config（含 token）**，无版本号/乐观锁；select/delete/reorder 无 in-flight 去重，并发到达时互相覆盖。
14. `index.html` `reorderAccounts`：hypergryph 分支本地重排时未按 `curGameId()` 过滤，`order` 含其它游戏账号 → **打乱其它游戏的排序**，与"按游戏独立存储"的设计矛盾。
15. `duplication.rs`：消费者在持 `dup` 锁期间做 Map + 全帧 BGRA→RGB / 面积平均，4K 下数毫秒 → **扫码与预览互斥阻塞**；`get_or_create` 还持 `shared()` 大锁创建 D3D11 设备（数十毫秒），期间所有消费者被串行化。
16. `lib.rs:956` `capture_preview` 是 `async fn` 但内部全程同步阻塞 → 占住 tokio 工作线程（同类问题适用于扫码路径）。

### P2 — 工程与可维护性

17. **CI 实际从未运行**：`.gitignore` 含 `/.github/workflows/`（注释："token 缺 workflow scope，暂不推送"）。`ci.yml` 存在于工作区但不入库，远端无任何自动化门禁。
18. **文档不入库**：`docs/` 被 gitignore。`发展总纲.md` 有 1,718 行 / 117 KB 的决策与变更记录，是极有价值的资产，但无法随仓库共享，也**无法在 CI/Code Review 中被引用**。
19. **测试覆盖不均**：`unit.rs` 56 个用例扎实覆盖了纯函数（QR 解析/编解码 16、crypto+DPAPI 8、config 6、签名 5、HLS/live 解析 12），但**网络层零 mock**：`official::scan`、`mihoyo::scan_confirm`、`get_oa_server` 三级回退、aigis 重试、getFp、`http.rs` 的重定向/chunked/双 TLS 栈全部无自动化用例，只能靠 7 个 `#[ignore]` 手动 probe。
20. **协议硬编码面大**：appkey/appsec/UA/版本号/预置 dispatch/`x-req-name=pc-1.4.7:80` 全部写死在 `constants.rs`。预置 dispatch 随游戏资源更新即过期（注释已警示）；官服强依赖 `passport_qr_url` 的 `tk`。**缺少契约测试，接口变更只能线上发现**。
21. **前端无工程化**：2,048 行单文件，无 lint / 类型 / 测试；`renderFilter()` 高亮顺序 bug；`startPreview()` 守卫过严（`paused`/`baseMapActive` 时回到前台永不恢复）；DPR 计算 `w -= w%4` 后 `(w/4)*3` 可能为小数；XSS 面（`innerHTML` 直接注入后端 SVG）；硬编码 CDN `static.geetest.com/v4/gt4.js`（内网必然失败）；无障碍近乎为零。
22. `clipboard.rs:71`：V5 头（124 字节）的 `BI_BITFIELDS` 未跳 12 字节 RGB 掩码 → 解析错位。
23. **许可证**：`zedbar` 为 LGPL-3.0-or-later（Cargo.toml 已注明"商用分发需评估"），与其余 MIT/Apache 依赖不同。
24. `lib.rs` 1,598 行承担 27 个命令 + 状态定义 + 窗口装配，职责偏胖，可拆 `commands/` 子模块。

## 六、改进建议（按性价比排序）

**第一梯队 — 直接止血（半天到一天）**

1. 删掉或脱敏 `bili.rs` 的响应日志（P0-1）。顺带全局排查是否还有把 token 打进日志的地方。

3. `duplication.rs` 补三件事：`mem::take` 改到 Map 成功之后（P0-2）、Map 段包 `catch_unwind`（P0-3）、`GetFrameMoveRects` 与 dirty 合并（P0-5）。
4. `live.rs`：`dec_fails` 成功时复位（P1-6）。

**第二梯队 — 结构性加固（数天）**

5. **给 http 层开一个注入口**：把 sdk 函数的 client 改成 trait/闭包注入，用 mock 覆盖 `scan_confirm`、官服两阶段确认、aigis 重试、OA 三级回退。这是当前最大的测试缺口，也是协议变更时唯一的早期预警手段。

7. 前端加乐观锁/版本号防并发写覆盖（P1-13），修 `reorderAccounts` 的游戏过滤（P1-14）。
8. `duplication.rs` 缩小锁粒度：Map 完成即放锁，转换移到锁外；`create_monitor` 移出大锁。

**第三梯队 — 长期健康**

9. 考虑把 `docs/` 中非敏感的决策记录（架构决策、踩坑清单）同步回仓库，或至少让 README 与总纲的关键决策保持一致。
10. 前端按职责拆分成几个 `<script type="module">` 或独立 js 文件，引入基础 lint。
11. 给 `constants.rs` 的硬编码参数加一个"协议版本自检"用例（例如 HEAD 探活关键端点），把"线上才发现"提前到"启动时发现"。

## 七、总体评价

这是一个**完成度高、工程密度大、性能优化有实测依据**的项目。四个模块（取帧 / 直播 / 扫码 / 协议）各自都有相当深入的技术处理，且每一处非常规做法都在注释里交代了原因——这在小众工具里很少见。

主要债务集中在三处：

- **并发与异常路径**：取帧层的锁粒度、Map 的异常安全、瓦片脏标记的丢失恢复，都属于"平时不犯、犯了就永久降级"的类型。
- **测试的结构性缺口**：纯函数覆盖扎实，但**网络交互层完全没有自动化**。而这个项目的正确性恰恰高度依赖第三方协议的细节（签名、端点、风控字段），一旦上游变更，没有任何机制能提前告警。
- **工程门禁空转**：CI 配置存在但不入库，`docs/` 沉淀了 1,700 行的决策记录同样不入库。知识在，但没有进入协作流程。

一句话：**实现能力明显高于工程保障能力**。补齐第二梯队的 5/6 两项（http 注入 + 真实 CI），投入产出比最高。
