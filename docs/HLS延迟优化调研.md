# HLS 延迟优化调研与选型

> 调研日期：2026-10-08。实测对象：B站 HLS-only 直播间（房间 6671755 / 5371145 / 1673630）。
> 目的：评估 HLS 路径能降到多低延迟，为后续优化选型。

---

## 1. 结论速览

- B站 HLS **不是真 LL-HLS**：苹果 LL-HLS 三件套（EXT-X-PART / PRELOAD-HINT /
  SERVER-CONTROL）**全部缺失**，只是传统 1 秒分片 HLS。
  → **partial segment / blocking reload 方案不可行**（服务端不支持）。
- HLS-only 房间无 FLV，**无法降级到 FLV 路径**。
- HLS 延迟的**根本下限 = 分片时长（1s）+ 生成等待**，无法突破。
- 当前实现额外叠加了「连接重建 + 固定 sleep + 轮询间隔」约 0.5~0.9s 浪费，
  **优化空间集中在这三处**。

---

## 2. 实测数据

### 2.1 B站 m3u8 标签统计（3 个真实房间）

| 标签 | 出现次数 | 含义 |
| --- | --- | --- |
| `#EXT-X-PART` | **0** | 部分分片（LL-HLS 核心） |
| `#EXT-X-PRELOAD-HINT` | **0** | 预加载提示 |
| `#EXT-X-SERVER-CONTROL` | **0** | 服务端控制（含 blocking reload） |
| `#EXT-X-MAP` | 1 | init 段（fMP4） |
| `#EXTINF` | 6~7 | 1.00s 分片 |

m3u8 结构（节选）：
```
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:1
#EXT-X-MAP:URI="h1791446463.m4s"
#EXT-BILI-AUX:12db275|K|3db66|1f88602
#EXTINF:1.00,3db66|1f88602
224228245.m4s
...
```

### 2.2 各环节耗时（房间 1673630）

| 环节 | 新建连接 | 持久连接（keep-alive） |
| --- | --- | --- |
| 拉 m3u8 | 142~209ms | **29~31ms** |
| 下载分片（391KB） | 408ms（首次）/ 45~76ms | 44~76ms |
| 快速重复新建连接 | ❌ `SSL: UNEXPECTED_EOF_WHILE_READING` | — |

**关键**：CDN 对**快速重复新建 TCP+TLS 连接直接拒绝**。持久连接拉 m3u8 提速 **~5 倍**。

### 2.3 当前代码结构

`http.rs` 每个请求都走 `request_bytes_sync`：
- `api_tls_connect(&host, port)` 新建 TCP+TLS
- 请求头写死 `Connection: close`

即：HLS 每拉一次 m3u8、每下一个分片，都**新建一次 TCP+TLS**（约 110~180ms 纯浪费）。

## 3. 方案对照

| 优先级 | 方案 | 预期收益 | 改动量 | 风险 |
| --- | --- | --- | --- | --- |
| **P0** | HLS 分片/m3u8 **连接复用**（keep-alive） | m3u8 150→30ms；避免 CDN 拒绝 | 中（新增持久连接 helper） | 低 |
| **P1** | 去掉固定 sleep，**按分片边界精确调度** | 省 200~500ms/轮 | 小 | 低 |
| **P2** | **分片预取**（提前下下一分片） | 与解码并行，省 1 个分片时长 | 中 | 中 |
| **P3** | 按 `TARGETDURATION/2` 节奏轮询 | 更快发现新分片 | 小 | 低 |
| ❌ | partial segment（EXT-X-PART） | 不可行（B站不支持） | — | — |
| ❌ | 降级 FLV | 不可行（HLS-only 房间无 FLV） | — | — |

---

## 4. 延迟下限推算

| 阶段 | 当前 | P0+P1 后 |
| --- | --- | --- |
| 分片生成等待 | ~1s | ~1s（不可压缩） |
| 发现新分片（轮询） | +0~300ms | +~150ms |
| 下载分片 | +50~120ms | +50~120ms |
| 连接重建 | +120ms | ~0（复用） |
| 固定 sleep | +200~500ms | ~0 |
| 解码 | +~300ms | +~300ms |
| **端到端** | **~1.5~2s** | **~1.1~1.3s** |

**理论上限约 1.1s**（受 1 秒分片粒度约束）。

---

## 5. 实施结果（2026-10-08，提交 053c84a）

P0~P3 **全部实施并实测**（房间 1673630）：

| 阶段 | 内容 | 实测效果 |
| --- | --- | --- |
| P0 | `http::KeepAliveConn` 连接复用 | m3u8 拉取 150→30ms（5 倍）；消除 CDN 拒绝重连 |
| P1 | 去掉固定 sleep，按分片边界调度 | — |
| P2 | 消费后仅 sleep 15ms 即重新轮询 | 省一个轮询间隔 |
| P3 | 无新分片时按 `target_duration/4` 轮询（250ms） | 更快发现新分片 |

**长时验证（70 秒）**：端到端延迟稳定 **0.3~0.4 分片 ≈ 333~429ms**，
2129 帧 ≈ 30fps 满帧，无累积漂移、无错误。

> 注：延迟观测改用「积压分片数」（服务端最新 seq − 已消费 seq）作代理——
> HLS 是整片下载后批量解码，样本级墙钟锚点法不适用（会得负值）。

**结论**：HLS 端到端延迟从 ~1.5~2s 降至 **~0.4s**（优于预估的 1.1~1.3s，
因 B站分片实际更新较快 + 连接复用消除大部分开销）。

**未做**：partial segment（EXT-X-PART）——B站 HLS 不下发，不可行。
