## 1. 项目定位

- **目标**：Windows 10+ 上，一个体积极小、启动极快、界面无冗余的《崩坏3》PC 端
  登录二维码扫码器。
- **核心场景**：用户已在自己手机上登录 B 站 / 米游社账号，游戏停在登录二维码界面；
  本工具截屏识别该二维码，用已保存的账号凭据向米哈游服务端提交扫码确认，完成登录。
- **支持渠道**：B 服（Bilibili）、官服（米哈游通行证）。其他渠道服（小米/华为/vivo/
  应用宝/WeGame 等）不在范围内（需逐个渠道实现 SDK 登录，工程量过大）。
- **明确非目标**：不做自动点击 / 一键登录 / 启动游戏、不做内嵌极验交互（仅提示）、
  不做自动更新、不做移动端 / macOS / Linux。

### 1.1 设计意图与用户旅程（2026-10-02 深入分析）

**根本意图**：把三个功能重叠、依赖沉重的参考项目（Python + PySide6 + OpenCV + Flask
+ PyInstaller）压缩成**只服务于「扫码登录崩坏3」这一个动作**的最小可用工具。体积从
数百 MB 降到十几 MB，启动从数秒降到近瞬时。

**设计哲学（隐含在代码取舍中）**：

1. **零学习成本**：不要求用户理解 B 服 / 官服的协议差异，工具在确认阶段自动逐个尝试
   已登录账号——这是「游戏码 URL 无法区分平台」这一客观限制下最省心的解法。
2. **零密码存储**：全程不接触、不落盘用户手机 App 里的密码；只保存扫码 / 密码登录
   获得的令牌，且令牌用 DPAPI 加密后落盘。
3. **高频零干扰**：挂机扫码时 CPU 占用极低（ROI 优先 / 降采样 / 帧指纹去重 / 节流四层
   优化），不抢占游戏资源。
4. **失败可恢复**：失败票据退避重试、轮询网络抖动保留会话、配置损坏自动备份重建——
   任何一环出问题都不至于让用户从头再来。

**典型用户画像**：双开 / 多号玩家，每天需切换多个账号；用 PC 端崩坏3，习惯用手机 App
扫码而非输入密码；对卡顿 / 闪退 / 复杂界面零容忍。

**核心价值主张**：比「拿起手机 → 打开 App → 找到扫一扫 → 对准屏幕」更快，尤其对
多账号用户——一次点击即完成从识别到登录的全过程。

**典型用户旅程**：

| 阶段 | 用户动作 | 工具响应 |
| --- | --- | --- |
| 首次使用 | 打开应用 → 点「添加账号」 | 弹窗二选一（二维码 / 密码） |
| 登录账号 | 用手机 App 扫工具生成的二维码 | 1.5s 轮询，展示「已扫码 / 已确认」 |
| 日常使用 | 游戏停在登录界面 → 点「开始扫码」 | 读剪贴板 → 全屏找码 → 自动渠道路由 → 确认 |
| 成功后 | — | 按配置清剪贴板 / 自动退出 |
| 进阶 | 缩小扫描区域 / 开启自动登录 | 降 CPU / 免手动点开始 |

## 3. 功能范围与关键决策

### 3.1 渠道与账号选择（2026-10-02 重大修正）

**核心事实（用户澄清 + 参考项目验证）**：

1. **游戏端只提供一个通用登录二维码**，任何渠道的扫码程序都能识别并完成登录。
   二维码 URL 形态为 `qr_code_in_game.html?ticket=...&app_id=...&biz_key=...&app_name=...`。
2. 参考项目 `bh3_login_simulation` 的 `QRScanner.parseUrl` **确实从二维码里解析
   `biz_key` / `app_id` / `app_name`**，其中：
   - `biz_key` 决定 `combo/panda` 端点前缀：`api-sdk.mihoyo.com/{biz_key}/combo/panda/qrcode/{scan|confirm}`；
   - `app_id` 写入 confirm 载荷（BH3 = 1）；
   - `app_name` 仅用于提示文案。

**因此本项目的正确做法**：

- **不需要「逐个渠道尝试」**——用哪个账号确认，就登录哪个账号。关键是**准确的账号选择**。
- 保留 B 服 / 官服各自的账号列表（同一渠道内单选），但**扫描确认时使用用户明确选定的账号**，
  不做「先试 B 服再试官服」的盲目轮询。
- 二维码中的 `biz_key` **应当被解析并用于构造端点**（当前实现硬编码 `bh3_cn`，
  虽然 BH3 两渠道的 `biz_key` 实测均为 `bh3_cn`，但按参考实现动态取更稳妥）。

**待定的实现细节**（执行优化时确认）：
- 若 B 服与官服账号同时存在，如何确定「当前用哪个」？候选方案：
  (a) 全局单一「当前账号」（跨渠道二选一）；
  (b) 保留 `active_bili` / `active_official`，但扫描时按 `biz_key` 或用户二次选择路由；
  (c) 保留双激活 + 逐个尝试作为「容错兜底」（但不作为主路径）。
- 目标：让「用哪个账号登录」对用户**完全可见、可控**，避免误用账号。

### 3.1.1 参考项目研读（`bh3_login_simulation-memories-dev`）

本项目基于该项目实现，以下为其关键机制（供后续参考）：

| 机制 | 参考实现 | 本项目对应 |
| --- | --- | --- |
| 二维码解析 | `QRScanner.parseUrl`：从 URL 拆 `ticket`/`app_id`/`biz_key`/`app_name` | `qr.rs::extract`（只取 ticket，**应补 biz_key/app_id**） |
| 渠道分发 | `LoginInstanceManager.genLoginImpl`：按 `server_type` 选择 `Official`/`Bilibili`/`Xiaomi`… 实现 | `config::Channel`（仅 Bilibili/Official） |
| 账号模型 | `RoleData`(open_id, combo_id, combo_token, channel_id, account_type) | `config::BiliToken` / `OfficialToken` |
| 扫码确认 | `QRScanner.genRequest`：Combo 用 bh_info，Account 用 uid+token | `scan.rs::confirm_in_game` |
| 端点构造 | `api-sdk.mihoyo.com/{biz_key}/combo/panda/qrcode/{scan,confirm}` | `constants::PANDA_SCAN_URL`（**硬编码 bh3_cn**） |
| 账号切换 | `official_slot` / 多渠道 slot 独立存储 | `active_bili` / `active_official` |
| 快速模式 | 记住上次成功数据，一键复用 | `last_server`（渠道记忆） |

> **注意**：参考项目支持全渠道（小米/华为/vivo/OPPO/UC/腾讯/WeGame 等 13 个），
> 本项目**仅保留 B 服与官服**（非目标，见第 1 节）。但若未来扩展，`LoginInstanceManager`
> 的「按 server_type 生成实现」模式可直接照搬。

### 3.2 扫描区域：**主窗口内实时监视器**（非独立 Overlay）
- 原 spec 规划「独立透明置顶红色范围框窗口」，实现改为**主窗口内折叠面板中的实时预览
  canvas**：滚轮缩放、左键拖拽平移，**可视视口即扫码区域**。
- 未手动缩放时默认**全屏多显示器**扫描。
- **决策**：采纳当前实现，删除 Overlay 规划。理由：单窗口方案交互更简单、无跨窗口坐标
  同步问题、无需点击穿透；对「选个大概区域」的需求足够。

### 3.3 剪贴板语义
- 「开始扫描」先读一次剪贴板图像 → 解码 → 若是可用游戏码则直接确认；否则回退区域检测。
- 只读当前项一次，不实现多历史项。

### 3.4 成功后动作
- 清剪贴板 / 自动退出，均为可持久化开关；退出前统一保存窗口位置。

## 5. 安全基线

1. **令牌落盘加密**：Windows 下用 DPAPI（`CryptProtectData`）包装 B 服的
   `access_key` 与官服的 `stoken`，密钥绑定当前用户，其它账户 / 机器无法解密。
   密文格式 `dpapi:<base64>`；旧版明文（无前缀）读取时兼容。解密失败置空，用户需重登。
   `mid`（用户 ID，非密钥）不加密。
2. **CSP 收紧**：仅保留 `'self'` + Tauri ipc + `data:`/`blob:`（二维码 SVG 内联），
   已移除全部未引用的第三方域名。
3. **`withGlobalTauri`**：当前保留（单文件前端需要），但 CSP 必须持续严格，且禁止引入
   任何外部脚本。
4. **密码命令节流**：`login_password_*` 加最小调用间隔（`LOGIN_MIN_INTERVAL_SEC = 3`），
   防脚本 / 误操作高频触发风控。
5. **日志脱敏**：服务端返回的 body/raw 不回显到前端日志，只回显 message。
6. **免责声明**：签名密钥/盐/RSA 公钥均来自公开项目，非密码学安全，仅自用/开源惯例实现。

## 7. 用户体验优化方向（2026-10-02 新增）

### 7.1 高价值（直接改善核心旅程）

1. **账号列表按最近使用排序**：当前按添加顺序；多号用户最常用的应置顶。

#### 问题 7 专项说明：B 站 SDK 弹窗登录可行性

- 参考项目 `Bilibili.java` 调用的是 **`com.bsgamesdk.android.BSGameSdk`**（B 站官方
  **Android** 游戏 SDK），弹窗是 Android 原生界面。
- **桌面端无法复用**：该 SDK 无 Windows 版本，且 B 站未提供桌面 OAuth 弹窗 SDK。
- 唯一理论可行路径是内嵌 WebView 加载 B 站网页登录页，但存在三个硬伤：
  1. B 站网页登录强制**极验验证码**，内嵌处理复杂；
  2. 需注入 JS 抓取 cookie/token，跨域与 CSP 限制多；
  3. 需放宽 CSP（`withGlobalTauri` 场景下**降低安全性**）。
- **结论**：不实现。保持「扫码登录 + 账号密码」两种；扫码是 B 站官方认可且最稳的路径。

### 2026-10-03 画质/抖动根治 + 窗口控制加固 + 死代码大清查

**预览画质与抖动（用户反馈：仍糊、静止时明显抖动）**：
- **抖动根因**：预览降采样用最近邻采样——桌面内容微动（如播放中的视频）时
  逐帧跳变采样点，表现为静止却闪烁/抖动。
- **修复**：Rust 侧改**面积平均降采样**（box filter，单次遍历 + x 箱查找表 +
  MonitorDup 上复用的累加缓冲，无逐帧分配）；前端源矩形整数对齐 +
  `imageSmoothingQuality: high`。
- **清晰度**：画布像素 = 显示 CSS 尺寸 × devicePixelRatio（1:1 物理像素，窗格
  清晰度物理上限）；源图按「画布宽 × 2 过采样 × 缩放」请求（≤1920），由浏览器
  高质量缩小。缩放放大的是绘制区域而非画布尺寸，采样链全程无成倍重采样。
- **占用**：数据帧节流到 30fps（同宽度 33ms 内的新帧回「未变化」；缩放档位
  切换不节流），60Hz 轮询 + 静止零成本架构不变。

**窗口控制加固**：

  「直接点击该元素」生效——点 logo 内 `<svg>` 时 target 是 svg，判定失败。

### 2026-10-04 固定居中 4:3 视口 + 暂停原分辨率底图

- `viewportFrac`：视口**恒为 4:3**，取「显示器居中 4:3 区域」——

### 2026-10-04 拖拽底图瓦片化（tile-based）全面重构

**背景**：拖拽/缩放时，旧方案每帧抓取并传输**整屏**低分辨率底图（1280 宽 ≈ 3.7MB/帧），
即便屏幕内容大部分静止，IPC 与 CPU/GPU 开销仍随全屏面积走。用户确认要「全局完整瓦片化」，
以大幅降低拖拽时的 CPU/GPU 占用。目标宽度用户实测 1920 略卡，定稿 **1280**。

**核心思路**：后端维护一块**持久整屏降采样底图**，仅对内容变化的**脏瓦片**降采样并回传增量；
前端维护本地底图 canvas，收到增量即 patch，拖拽从本地采样（零传输）。实时预览路径**完全不变**（风险隔离）。

**后端（src-tauri/src/duplication.rs）**：

| 项 | 说明 |
| --- | --- |
| 常量 `TILE_PX = 64` | 瓦片像素尺寸；1280×720 → 20×12=240 块 |
| 类型别名 `TileUpdate` / `TileDelta` | 修复 clippy `type_complexity` |
| `TileState` | 持久整屏 RGBA 底图 `base`、待更新标记 `dirty`、网格 `cols`/`rows`；`resize()` 尺寸变化重建并全标脏 |
| `MonitorDup` 新字段 | `tiles: TileState`、`tile_mode: bool`、`tile_want: bool` |
| `grab_new` 瓦片分支 | **消费门控**（`tile_want` 为假则跳过）+ **只拷贝脏瓦片源包围盒**（`dirty_src_bbox` → `CopySubresourceRegion`，非整屏） |
| `mark_dirty_tiles()` | 用 `GetFrameDirtyRects` 把脏矩形映射到瓦片网格；取失败时保守全标脏；**0 个脏矩形 = 无变化，不标脏** |
| `tile_delta(max_tw)` | 只处理落在已拷贝 bbox 内的脏瓦片；面积平均降采样 + **逐像素哈希对比**（内容未变不发）；末尾仅保留越界待处理标记 |
| 公开 API | `set_tile_mode(region,on)`、`tile_frame(region,max_tw)` |

**后端（src-tauri/src/lib.rs）**：新增命令 `capture_tiles`（负载：8 字节头 tw/th + 每瓦片
16 字节头 col/row/w/h + RGBA；无变化返回 8 字节）与 `set_tile_mode`，均已注册。

**关键修复**：`set_tile_mode` 每次**开启**（新一次拖拽）都强制全量标脏——前端起手会重建底图
canvas，需一次性铺满全部瓦片，否则只收到零星脏瓦片 → 大面积黑屏（第二轮拖拽起手必现）。

**前端（src/index.html）**：`BASE_MAP_TARGET = 1280`、`TILE_PX = 64`（须与后端一致）；
新增 `patchTiles(buf)`（解析二进制增量，1:1 `putImageData` 到持久底图瓦片位置，尺寸变化重建 canvas）、
`tileLoop()`（每帧调 `capture_tiles`，patch 后拖拽中重绘，绝对周期调度）；
`startBaseMap()`/`stopBaseMap()` 经 `set_tile_mode` 开关后端瓦片模式；
`captureBaseMap` 保留给暂停态的独立原始分辨率截取。

**预期收益**：拖拽时屏幕内容大多静止 → 绝大多数瓦片缓存命中，IPC 从整屏 ≈3.7MB/帧
降到几十 KB/帧；后续可加「脏面积超阈值降级全量」「`GetFrameMoveRects` 优化移动」。

**验证**：`cargo build` / `cargo clippy -D warnings` / `cargo test`（36 项）通过；
前端内嵌 JS `node --check` 通过；release 体积 9.14MB，启动正常（内存 ≈67MB）。

### 2026-10-04 体积裁剪 + 图标/窗口 + 缩放闪烁根治

**体积裁剪（9.14MB → 8.82MB）**：

| 措施 | 效果 |
| --- | --- |
| `env_logger` 关闭默认特性（去 `env_filter`） | 移除正则栈（regex_automata + regex_syntax + aho_corasick ≈ 742KB） |
| `rxing` 关闭默认特性 | 移除全套图片解码器（gif/jpeg/tiff/webp/avif...，仅内存 RGB 解码不需要） |

**LTO 取舍**：曾试 `lto="thin"` + `codegen-units=1`，体积仅再减 ~0.3MB，
但单次 release 构建从 ~1 分钟增至 ~12 分钟，收益不成比例，**已移除**。

**单 exe 交付**：release 目录仅 exe + `.pdb`（调试符号，发布可删），无任何 DLL，exe 自包含；
唯一前提是目标机有 **WebView2 运行时**（Win11 内置，Win10 多数随 Edge 已装）。

**5MB 目标评估**：经 `cargo-bloat` 实测，当前构成中自身代码 2.0MB、`rxing` 884KB、
`std` 593KB、tauri 框架 ~800KB、reqwest 275KB、两个 `image` 库 ~600KB 均为硬骨头。
压到 5MB 只能做架构级换库（rxing→rqrr、screenshots→原生 Win32 GDI、arboard→原生剪贴板），
**均会触及扫码/截图/剪贴板核心链路**，与「功能不受影响」冲突，**决定不强求**。

**图标与窗口**：
- 根目录 `icon.png` 经 `cargo tauri icon` 生成全套图标（ico/icns/各尺寸 png/mipmap）。
- 窗口固定 **300×500**（`tauri.conf.json` 设 `resizable: false`）。

**缩放/拖拽闪烁根治**（多轮定位）：

- **错误尝试**：加「收尾防抖延迟」（视图稳定后延迟恢复实时）——反而延长底图停留，
  使闪烁**更剧烈**。
- **真正根因**：收尾切回实时时，`srcCanvas` 仍是停预览期间的**旧视口**实时帧，
  从「底图（内容正确）」切到「旧实时帧（内容错位）」→ 跳变闪。
- **最终方案**：
  1. 回滚防抖延迟；
  2. 收尾后**保持底图**，等实时帧真正更新到当前视口（`pendingRealtime` 标志，
     `refreshPreview` 收到新帧时清除）再切换显示源；
  3. 统一用 `viewDirty`（视口是否已变化）门控采样源——起手/未移动用实时帧、
     拖拽/缩放中及收尾等实时用底图；
  4. `startPreview` 增加 `baseMapActive` 守卫，避免底图模式期间被误启动。

/ `node --check` 全通过；release 体积 **8.82MB**，启动正常（内存 ≈87MB）。

### 2026-10-06 直播卡顿根治 + CPU 再降（用户实测反馈两项）

**卡顿根治——弹出节拍与到达节拍解耦**：用户实测「提高延迟并未提高流畅度」点破了
根因——此前「到达即弹出」（哪怕有缓冲），网络抖动直接透传到显示。改为**固定节拍

延迟自适应收敛。缓冲上限 6 帧 ≥ 用户要求的 5 帧深度。

1. 直播预览轮询 60→30fps（IPC 与降采样成本减半）；
2. 重复帧短响应：后端缓存 (seq, 裁剪区, 输出宽)，帧未变时返回 24 字节空头

3. 扫码链路降本：`take_scan_frame` 改为**当前显示视口**裁剪 + 2×2 平均半尺寸 RGB

### 2026-10-06 修复：连接直播间闪退回屏幕

**根因**：上一轮把「缓冲欠载」误判成「会话结束」——流帧率（约 25fps）低于显示

### 2026-10-07 直播追帧：修复长跑延迟漂移（用户实测反馈）

**问题**：直播预览开头延迟远低于浏览器，但运行一段时间后延迟反超浏览器。
根因不是「追帧概率失败」——是**根本没有追帧机制**：解码线程按 socket 顺序逐 tag
读取，解码吞吐 < 流码率（尤其 1080p60）时 socket/TCP 缓冲单调积压，读取位置持续落后
直播边缘，延迟只增不减。帧队列（≤6 帧）只是显示缓冲，管不到网络积压。

**修复（两层）**：
1. **追帧**（`decode_session`）：以 FLV 媒体时间戳 vs 到达墙钟测落后量——
   锚点记录「首个视频 tag 时间戳 + 到达时刻」，推算此刻应有的媒体时间戳，差值即滞后。
   滞后 > `CATCHUP_LAG_MS`(1200ms) 即进入追帧态：只读不解码快速排空 socket 缓冲，
   遇下一个关键帧（IDR）重建解码器（重喂缓存的 SPS/PPS）恢复，锚点重置。
   实测延迟稳定压在 ~1.2s，不再单调增长。
2. **自动降清晰度**（`decode_loop`）：某会话累计追帧达 `CATCHUP_LIMIT`(4) 次，判解码吞吐
   持续不足，降级清晰度重试（复用 `QN_CHAIN` 10000→800→450→150）。已是最低档则继续
   运行（追帧已能维持延迟，重连反而中断画面）。实测高码率流自动 `10000→800→450` 后
   追帧归零，稳定运行。

**验证**：长跑探针 `probe_live_lag`（新增）——滞后稳定 1.2s、降级链正常、450 档追帧 0 次；
批量回归成功房间扫码帧仍 100%；43 单测 + clippy -D warnings + fmt 全过。

### 2026-10-07 清晰度档位链修正（用户实测反馈某房间慢放/延迟）

**问题**：用户实测房间 1937006066 画面慢放、延迟偏高。

**根因**：
1. `QN_CHAIN` 硬编码 `[10000, 800, 450, 150]`，其中 **800 / 450 不是 B站标准档位**
   （标准为 10000/400/250/150/80）——请求时被 B站**回退到原画**，降级静默失效。
2. 不同房间档位不同：`accept_qn` 可能是 `[10000]`（仅原画）或 `[10000,400,250,150]`。
   固定链对「仅原画」房间会反复请求不存在的档位 → 无效重连。

**修复**：
- 新增 `parse_accept_qn`：从 playinfo 解析房间**实际提供**的档位（http_stream/flv/avc）。
- `build_qn_chain` / `fetch_qn_chain`：据此构建降级链（仅取 ≤10000 档，降序去重）；
  「仅原画」房间链长为 1，不降级。`decode_loop` 改用动态链，日志打印实际链。

**附带排查**：
- 试开 openh264 多线程解码（`num_threads`）提速 1080p——**Windows 实测必崩**
  （STATUS_ACCESS_VIOLATION / 0xc0000005），已回退；库方文档亦警告会 segfault。
- 关键结论：**release 构建下单线程解码已足够**——探针实测 10684457（1080p 仅原画）
  release 下解码达 60fps、追帧 0 次；此前 debug 探针显示的「追帧频繁」主要是 debug
  构建（Rust 拷贝/转换未优化）的假象。

**验证**：release 探针实测房间 10684457（1080p）0 追帧、60fps；新增 `parse_accept_qn`
单测；44 单测 + clippy -D warnings + fmt 全过。

### 2026-10-07 延迟漂移根治 + HTTP 层重构 + 体积达标（用户实测反馈两项）

### 2026-10-07 解码性能根治（NASM 中文路径）+ 体积回达标

**① 慢速播放/延迟漂移的真正根因（用户实测反馈）——NASM 汇编从未生效**：

- 追帧机制本身工作正常（输出侧追帧已能压制），但用户反馈「追完仍在高延迟处」。
  进一步排查构建产物发现：**openh264 的 x86 汇编加速一直编译失败并被静默降级**
  （build 输出：`Failed to compile NASM files, not using any assembly`），
  纯 C 解码比汇编慢约 2.7 倍 → 1080p60 流解码吞吐仅 ~0.6× 实时率 → 积压持续 →
  追帧频繁且追不回直播边缘。
- **根因**：nasm 无法打开含**非 ASCII 字符**的路径——本项目目录名 `崩坏3扫码器`
  即触发（`nasm: fatal: unable to open input file ... 崩坏3扫码器 ... No such file
  or directory`；同一文件在 ASCII 路径下编译成功、绝对/相对路径均如此、nasm 2.16）。
  nasm-rs 传绝对路径 → 必然失败 → openh264-sys2 静默退回纯 C 编译。
- **修复**：vendor 化 `openh264-sys2`（`[patch.crates-io]` 指向 `vendor/openh264-sys2`），
  改写其 build.rs 的 NASM 段：把 asm 源与 `asm_inc.asm` include **复制到 %TEMP% 下的
  ASCII 暂存路径**（`oh264_asm_stage`）再调 nasm 编译，产物回传链接；失败不再静默
  （打印 `NASM FAILED`，保留降级容错）。
- **实测效果**（房间 3074443，1920×1080）：
  - 单帧解码 ~16ms → **~10ms**；房间 6（854×480）~2~3ms；
  - 媒体速率 **1.00× 墙钟**（此前 0.60×）、**输入/输出滞后恒 0ms**、35 秒长跑**零追帧**。
  - 结论：解码跟得上流码率，延迟稳定在直播边缘（此前「几秒后漂移」的根因即解码积压）。

**② 移除无效的边缘探测看门狗**（上一轮尝试）：跨连接的媒体时间戳零点各自独立
（探测连接从 19ms 起、解码连接在自己的时间轴上），跨连接求差毫无意义——实测 gap
恒为回绕巨大值、每 6 秒误触发一次跳帧。已移除，恢复**墙钟锚点追帧**作为安全网
（asm 生效后正常流滞后恒 0 不误触发；码率提升/性能不足时仍能兜底）。

**③ 体积回达标（5.16MB → 4,980,224 bytes = 4.98MB）**：

- 图标 `icon.ico` 128 色量化（16 万→12.8 万色内，134KB → 75KB，视觉无损）。
- 注：vendor 目录（6.5MB 源码）为构建必需，纳入版本控制；编码器源保留
  （链接器已在 LTO 下消除 encoder 目标码，未见体积收益风险）。

**验证**：44 单测 + 1 smoke、clippy -D warnings、fmt、node --check 全过；
全部真实网络链路探针通过；长跑实测（房间 6 / 3074443）解码速率 1.00×、零追帧；
release 4,980,224 bytes。
